# Отчёт: Этап 3 — brute force и метрики качества

- **Дата:** 2026-10-27
- **Этап и задачи плана:** Этап 3, задачи 3.1–3.3
- **Предыдущий отчёт:** `docs/reports/2026-10-27_03_backend_etap-2-sloj-dannyh.md`

## 1. Краткое резюме

Реализован пакет `internal/bruteforce` — точный k-NN поиск линейным сканом (последовательно и параллельно), а также функция recall@k для сравнения с приближённым HNSW-поиском. Добавлен пакет `internal/benchmark` с метриками качества: перцентили задержки p50/p95/p99, QPS, время построения индекса и оценка используемой памяти. Это закрывает Этап 3 и даёт измерительную базу для Главы 3 курсовой (сравнение HNSW с полным перебором).

## 2. Что сделано

- 3.1 `internal/bruteforce` — точный k-NN: линейный скан всех векторов, `Result{ID, Dist}`, сортировка по расстоянию с тай-брейком по id; параллельный режим через `NewWithWorkers` (векторы делятся на непрерывные диапазоны, каждый воркер возвращает свой top-k, результаты сливаются и сортируются). `Search` клампит `k` к `N`, корректно обрабатывает `k <= 0` и несовпадение размерности; `Recall` считает recall@k по множеству id.
- 3.2 recall@k против brute force — интеграционный тест `TestHNSWQualityMetrics` (пакет `internal/benchmark`): строится HNSW-индекс, для каждого запроса exact-эталон берётся из `bruteforce`, recall считается через `bruteforce.Recall`. Получено recall@10 = 1.0000 (n=3000, dim=16, M=16, efC=100, efSearch=50, 30 запросов).
- 3.3 Метрики — `internal/benchmark`: `Percentile` (линейная интерполяция между ближайшими рангами), `LatencyFromSamples` (p50/p95/p99 + QPS = 1000 / средняя задержка в мс), `MeasureBuildTime`, `HeapInUse` (heap in-use после принудительного GC — оценка памяти индекса). Тесты метрик и бенчмарки brute force (последовательный и параллельный).
- Попутно: тип результата поиска HNSW экспортирован (`hnsw.Result` с полями `ID` и `Dist`) вместо внутреннего `item` — без этого результаты `Search` нельзя было использовать в другом пакете (сравнение с bruteforce, будущий HTTP API). Алгоритм и поведение не менялись, это чисто переименование типа/полей.

## 4. Ключевые решения

- **Решение:** `bruteforce` принимает `DistFunc` — алиас на `func(a, b []float32) float32`, поэтому `hnsw.SquaredL2`/`hnsw.DistanceFunc` подходят напрямую.
  **Альтернативы:** импорт `hnsw` ради типа `Metric`; собственный отдельный тип функции.
  **Причина:** отсутствие циклической зависимости между пакетами (`hnsw` ничего не знает про `bruteforce`), при этом метрика гарантированно та же, что у индекса.
- **Решение:** параллельный скан делит векторы на непрерывные диапазоны; каждый воркер отдаёт свой top-k, после чего результаты сливаются и сортируются с тай-брейком по id.
  **Альтернативы:** один общий heap с мьютексом; динамическая балансировка задач.
  **Причина:** результат детерминирован и совпадает с последовательным (проверено тестом), а блокировок на горячем пути нет; для равномерной стоимости расстояний балансировка не нужна.
- **Решение:** recall@k = |exact top-k ∩ approx top-k| / min(k, len(exact)), сравнение по множеству id.
  **Альтернативы:** сравнение по порядку (rank-aware).
  **Причина:** классическое определение recall в ANN-литературе; порядок внутри top-k не важен.
- **Решение:** перцентили — линейная интерполяция между ближайшими рангами, QPS = 1000 / средняя задержка (мс).
  **Альтернативы:** nearest-rank перцентиль; QPS = 1 / p50.
  **Причина:** устойчивые и воспроизводимые значения на малых выборках; QPS по среднему согласуется с суммой времён запросов.
- **Решение:** память индекса измеряется как `HeapInUse()` до/после построения (GC форсируется), индекс удерживается живым.
  **Альтернативы:** формульная оценка по числу узлов и степеням; `pprof`.
  **Причина:** честный runtime-замер без привязки к деталям структуры; формулу можно добавить в Этапе 4 при необходимости.

## 6. Проблемы и ограничения

- `bruteforce.Index` хранит ссылку на переданный срез векторов; изменение данных после `New` не поддерживается (задокументировано в комментарии).
- Параллельный скан статически делит диапазоны; при сильно неравномерной стоимости расстояний возможен дисбаланс (для L2/cosine несущественно).
- Измерение памяти через `HeapInUse` включает шум GC и накладные расходы рантайма — это оценка, а не точный размер структуры.
- `gofmt` поправил выравнивание в `internal/hnsw/index.go` и `trace.go` (несоответствие осталось с предыдущих этапов); логика не затрагивалась.
- Пакет `internal/benchmark` создан уже на Этапе 3 (минимум для метрик 3.3); параметрическая сетка и экспорт результатов (Этап 4) будут надстроены над ним.

## 7. Изменения контракта API / влияние на другую часть

- HTTP-контракт `docs/API.md` не менялся.
- Go-API `internal/hnsw`: `Search` и `SearchWithTrace` теперь возвращают `[]hnsw.Result` с экспортируемыми полями `ID` и `Dist` (раньше — неэкспортируемый `item`). Это важно для Этапа 5 (HTTP API): обработчики смогут напрямую формировать ответ. Сигнатуры и семантика не изменились, поведение идентично.
- Новые пакеты `internal/bruteforce` и `internal/benchmark` будут использоваться в Этапе 4 (сетка параметров, QPS/задержки/ускорение) и Этапе 5 (`mode: bruteforce` в `/search`, `/benchmark`). Frontend-агента изменения не затрагивают.
