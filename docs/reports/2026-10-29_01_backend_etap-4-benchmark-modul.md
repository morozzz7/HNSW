# Отчёт: Этап 4 — модуль бенчмарков (сетка параметров, сравнение с перебором, масштабирование, экспорт)

- **Дата:** 2026-10-29
- **Этап и задачи плана:** Этап 4, задачи 4.1–4.6
- **Предыдущий отчёт:** `docs/reports/2026-10-27_04_backend_etap-3_bruteforce-metrics.md`

## 1. Краткое резюме

Пакет `internal/benchmark` расширен до полноценного модуля экспериментов: запуск сетки `M × efConstruction × efSearch` (с дополнительными осями `metric` и `heuristic`), расчёт recall@k, QPS, задержек p50/p95/p99, времени построения и ускорения относительно точного перебора, отдельный прогон «время запроса от размера данных N» и экспорт результатов в JSON/CSV. Это закрывает Этап 4 и даёт готовые таблицы и сырые данные для Главы 3 курсовой; HTTP-эндпоинты Этапа 5 не реализовывались.

## 2. Что сделано

- **4.1 Сетка параметров.** `RunGrid(GridConfig) ([]Result, error)` перебирает `M`, `EfConstruction`, `EfSearch`, а также (расширение) `Metric` и `UseHeuristic`. Для одной комбинации `(M, efConstruction, metric, heuristic)` индекс строится один раз и переиспользуется для всех `efSearch`; точный эталон `bruteforce` считается один раз на метрику. Порядок строк детерминирован: `M → efConstruction → metric → heuristic → efSearch`. Есть необязательный колбэк `Progress(done, total)` для будущего SSE.
- **4.2 Метрики результата.** `Result` содержит `M`, `EfConstruction`, `EfSearch`, `Metric`, `UseHeuristic`, `K`, `Recall`, `QPS`, `LatencyP50Ms/P95Ms/P99Ms`, `BuildTimeMs`, `BruteforceQPS`, `Speedup`. Recall считается через `bruteforce.Recall`, QPS и перцентили — через существующие `LatencyFromSamples`/`Percentile`, время построения — через `MeasureBuildTime`.
- **4.3 Heuristic vs simple.** Ось `UseHeuristic []bool` позволяет в одной сетке сравнить `SELECT-NEIGHBORS-HEURISTIC` (Алг. 4) и `SELECT-NEIGHBORS-SIMPLE` (Алг. 3); флаг попадает в каждую строку результата.
- **4.4 Сравнение метрик.** Ось `Metric []hnsw.Metric` поддерживает `l2`, `cosine` и `inner_product`; эталон перебора строится с той же функцией расстояния, что и индекс.
- **4.5 Масштабирование.** `RunScaling(ScalingConfig) ([]ScalingResult, error)` измеряет QPS, задержки, recall, время построения и ускорение для списка `N`. По умолчанию `N = [1k, 10k, 100k, 1M]`, но список, число запросов, `k`, `M`, `efConstruction`, `efSearch`, метрика, распределение и seed настраиваются. Данные и запросы генерируются детерминированно через `dataset.Generate` (данные — `Seed`, запросы — `Seed+1`).
- **4.6 Экспорт.** `WriteJSON(w, v)` / `WriteCSV(w, results)` пишут в любой `io.Writer`; `WriteJSONFile`, `WriteCSVFile`, `WriteScalingCSV`, `WriteScalingCSVFile` — обёртки для файлов. CSV имеет стабильный заголовок и одну строку на результат; JSON использует `recall@<k>` в соответствии с контрактом `POST /benchmark`.
- **Устойчивое измерение времени.** Из-за грубого разрешения часов на машине разработки одиночный быстрый запрос часто измерялся как 0 мс (QPS = 0). Добавлена калибровка: каждый замер — среднее по нескольким подряд идущим вызовам; число повторов подбирается удвоением так, чтобы минимум из 5 проб был не меньше 1 мс (не более 4096 повторов). Это затронуло и существующий интеграционный тест Этапа 3 — он переведён на общие функции `measureExact`/`measureSearch`.
- **Тесты.** Добавлены тесты сетки (малая сетка, значения по умолчанию, детерминизм recall, ошибки валидации), масштабирования (малые N, прогресс, ошибки), экспорта (заголовок CSV, ключ `recall@k` в JSON, файловые обёртки, проброс ошибки writer'а). Все тесты быстрые (`go test ./internal/benchmark` ≈ 2.3 с).

## 4. Ключевые решения

- **Решение:** индекс строится один раз на `(M, efConstruction, metric, heuristic)` и переиспользуется для всех `efSearch`; точный эталон `bruteforce` считается один раз на метрику.
  **Альтернативы:** перестраивать индекс для каждой строки сетки; считать эталон для каждой строки.
  **Причина:** время построения в строке относится ко всей группе, а пересчёт эталона не меняется от `efSearch`; это кратно ускоряет сетку без потери корректности.
- **Решение:** JSON сериализует recall под динамическим ключом `recall@<k>` (через `MarshalJSON`), а CSV — под стабильным столбцом `recall` с отдельным столбцом `k`.
  **Альтернативы:** всегда `recall` + `k` в JSON; всегда динамический ключ в CSV.
  **Причина:** JSON должен напрямую совпадать с контрактом `POST /benchmark` (`recall@10`), а CSV должен иметь одинаковый заголовок при любом `k`, чтобы таблицы в отчёте были стабильными.
- **Решение:** калибровать замеры повторными вызовами (минимум 5 проб, порог 1 мс, до 4096 повторов).
  **Альтернативы:** доверять одиночному `time.Now`/`time.Since`; измерять только суммарное время всего набора запросов.
  **Причина:** на текущей машине разрешение часов очень грубое, и одиночные запросы в 10–50 мкс часто давали 0; суммарное время не даёт перцентилей. Калибровка сохраняет и QPS, и p50/p95/p99, хотя значения задержек всё равно квантованы.
- **Решение:** масштабирование генерирует данные через `dataset.Generate` с одним seed на точку N; запросы генерируются один раз (`Seed+1`) и используются для всех N.
  **Альтернативы:** загружать внешний датасет; генерировать новые запросы для каждого N.
  **Причина:** воспроизводимость, отсутствие больших файлов в репозитории и одинаковые условия сравнения; для `uniform`/`gaussian` данные для меньшего N являются префиксом данных для большего N.
- **Решение:** экспорт вынесен в функции с `io.Writer` и отдельными файловыми обёртками.
  **Альтернативы:** только запись в файл; только HTTP-хендлер.
  **Причина:** один и тот же код может использовать и CLI/эксперимент, и будущий HTTP-эндпоинт без дублирования.

## 6. Проблемы и ограничения

- **Грубые часы.** На машине разработки разрешение `time.Now`/`time.Since` очень грубое: без калибровки быстрые запросы давали 0 мс и QPS = 0. Калибровка (минимум 5 проб по 1 мс, до 4096 повторов) делает значения ненулевыми и стабильными, но задержки всё равно квантованы (например, p50 = 0.0625 мс, 0.125 мс), а QPS — оценка, а не точное значение. Абсолютные цифры зависят от окружения.
- **Один прогон на конфигурацию.** Время построения и QPS не усредняются по нескольким повторам: сетка из 18 точек и так занимает секунды. Для итоговых таблиц курсовой имеет смысл повторить ключевые точки 3–5 раз и взять медиану.
- **Baseline перебора.** Реализация `bruteforce` Этапа 3 на каждом запросе сканирует все векторы, сортирует весь массив кандидатов и только потом обрезает его до `k`. Поэтому `bruteforceQps` и `speedup` в таблицах отражают именно эту реализацию, а не оптимизированный top-k/heap; против оптимизированного точного поиска ускорение было бы меньше.
- **1M не проверен.** Масштабирование реализовано для любого списка N, включая 1M, но фактический прогон 1M не выполнялся из-за времени и памяти.
- **Память по строкам не измеряется.** `HeapInUse` из Этапа 3 остаётся доступным, но в `Result` не включён: измерение памяти для каждой точки сетки удорожает прогон и сильно шумит.
- **Валидация сетки** использует `dataset.Validate` и лимиты `MaxVectors = 1_000_000`; для больших N в `RunScaling` лимит датасета не применяется (генератор создаёт данные напрямую).
- **`UseHeuristic` в `ScalingConfig`** — обычный `bool`; нулевое значение означает простую эвристику. Для значения по умолчанию (heuristic) нужно использовать `DefaultScalingConfig()` или явно выставить `UseHeuristic: true`.

## 7. Изменения контракта API / влияние на другую часть

Изменений `docs/API.md` нет. `benchmark.Result` уже содержит JSON-поля строки `POST /benchmark` (`M`, `efConstruction`, `efSearch`, `qps`, `latencyP50Ms/P95Ms/P99Ms`, `buildTimeMs`, `bruteforceQps`, `speedup`) и сериализует recall как `recall@<k>`, поэтому Этап 5 может маршалить `[]benchmark.Result` напрямую. Дополнительно в JSON попадают `metric`, `heuristic`, `k` — это расширение, не ломающее контракт. Для SSE можно использовать `GridConfig.Progress(done, total)`.

## 9. Следующие шаги
